# M2 · 干员部署实现说明

本阶段把「把干员摆到战场上」这件事拆成 5 个函数，并额外用拖拽做了一套更顺手的部署交互。

---

## 一、数据结构（框架已给好）

干员属性用**几张下标对齐的数据表**管理，同一个下标 = 同一个干员：

| 表 | 含义 |
| --- | --- |
| `OP_NAME` | 干员名字 |
| `OP_ROLE` | 职业（狙击 / 重装 / 术师） |
| `OP_COST` | 部署费用 |
| `OP_ASSET` | 美术前缀 |

因为「同一干员同时最多一个在场」，场上状态也直接按干员编号存：

```cpp
bool onField[OP_COUNTS];      // 是否在场
int  opRow[OP_COUNTS];        // 在场时所在行
int  opCol[OP_COUNTS];        // 在场时所在列
float opCooldown[OP_COUNTS];  // 再部署冷却（秒）
```

---

## 二、五个任务函数

### 1. `isCellOccupied` —— 这格有没有人

遍历所有干员，只要有一个「在场 + 行列都对上」，就说明这格被占了。

```cpp
for (int op = 0; op < OP_COUNTS; ++op)
    if (onField[op] && opRow[op] == row && opCol[op] == col)
        return true;
return false;
```

### 2. `canPlaceHere` —— 地形允许放吗

规则只有两条，但必须先判越界再读 `map`：

- 越界 → `false`；
- 重装（近战）只能站地面 `'#'`；
- 狙击 / 术师（远程）只能站高台 `'P'`。

```cpp
const char tile = map[row][col];
if (OP_ROLE[op] == OP_DEFENDER) return tile == '#';
return tile == 'P';
```

`S`、`E`、`.` 都不属于这两种，所以自然放不上。

### 3. `placeOperator` —— 真正上场

只做「记录」这一件事，不判断能不能放：

```cpp
onField[op] = true;
opRow[op]   = row;
opCol[op]   = col;
```

### 4. `tryPlaceOperator` —— 部署主逻辑

把前面几个函数串起来，**四个条件全过才落地**，并按顺序检查（越早失败越省事）：

```text
编号合法 → 该干员不在场 → 地形合法 → 该格没人 → 费用够
                ↓ 全过
        扣费 + placeOperator
```

任何一步失败都直接 `return false`，**不扣费**。

### 5. `retreatOperatorAt` —— 撤退

找到站在这一格的干员后：

- 返还**一半**部署费用：`dp += operatorCost(op) / 2`；
- 进入再部署冷却：`opCooldown[op] = DEPLOY_COOLDOWN`；
- 下场：`onField[op] = false`。

这一格没人就返回 `false`。

## 三、（Vibe Coding）拖拽部署

原始框架是「点干员卡 → 点格子」两步操作。拖动版本改成「按住卡片拖到目标格松手」。

### 1. 状态

```cpp
int   dragOp;      // 正在拖的干员（-1 = 没有）
bool  dragging;    // 是否真的拖起来了
sf::Vector2f dragStartPos, dragPos;
const float DRAG_START_DIST = 8.f;   // 移动超过 8 像素才算拖动
```

**为什么要区分 `dragOp` 和 `dragging`？**
按下卡片时只是「可能想拖」，如果立刻进入拖动状态，普通点击选卡也会被当成拖拽。所以要等鼠标移动超过阈值，才把 `dragging` 置为 `true`——这样「点选」和「拖动」两套操作可以共存。

### 2. 三个鼠标事件

| 事件 | 处理 |
| --- | --- |
| `MouseButtonPressed` | 点在卡片上 → 记录 `dragOp`、起点坐标 |
| `MouseMoved` | 更新 `dragPos`；位移超过阈值 → `dragging = true` |
| `MouseButtonReleased` | 若在拖动：换算成行列，走 `tryPlaceOperator`；否则只清状态 |

松手时和点击部署一样，先过一遍「不在场 + 冷却结束」，再交给 `tryPlaceOperator` 做真正的判断——**规则只有一份，拖动和点击共用**。

### 3. 视觉反馈

`drawDragging()` 每帧画两样东西：

- 鼠标所在格的高亮框：绿 = 可放，红 = 不可放（用和部署完全相同的条件算出来）；
- 半透明的干员贴图跟着鼠标走，表示「还没放下」。

## 四、心得

- **函数要分工明确**：`canPlaceHere` 只判断地形，`isCellOccupied` 只判断占位，`placeOperator` 只负责记录。主逻辑 `tryPlaceOperator` 才能一眼看懂。
- **判断顺序影响可读性**：先便宜、先容易失败的检查放前面（编号 → 在场 → 地形 → 占位 → 费用）。
- **状态要成对维护**：`onField` 和 `opRow/opCol` 必须一起改，否则会出现「在场但坐标是旧的」这种幽灵状态。
- **交互层要复用逻辑层**：拖拽和点击都调用同一套 `tryPlaceOperator`，才不会出现「拖动能放、点击不能放」的不一致。
- **区分「意图」和「动作」**：按下卡片只是意图，移动超过阈值才是动作（`dragOp` vs `dragging`），这是拖拽交互的关键。
